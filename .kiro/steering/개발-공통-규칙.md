# 개발 공통 규칙 (Steering)

이 문서는 HANARO Payload 개발에서 모든 Spec·코드에 공통으로 적용하는 규칙이다.
근거 문서: `sources/00_CURRENT_STATE.md` v2.0, `sources/07_FUTURE_DEVELOPMENT_PLAN_v3.0_VISION_DESCENT(2).md`, `KIRO_DEVELOPMENT_PROPOSAL.md`.

## 1. 상태 문서 우선순위
- `sources/00_CURRENT_STATE.md`가 최우선 상태 문서다. 여기서 `미확인`·`가정`·`작업 결정`으로 분류된 항목을 확정 사실로 다루지 않는다.
- 팀이 승인한 임무 요구조건(`01_REQUIREMENTS_BASELINE.md`)은 아직 없다. Kiro가 생성한 소프트웨어 요구사항을 승인된 임무 요구조건으로 승격하지 않는다.

## 2. 승인 요구조건과 가정의 분리
- 하드웨어 입력(부품·핀·전압·표적 색·투영 치수)은 값이 없으면 **가정** 또는 **설정값**으로 명시하고, 확정값처럼 쓰지 않는다.
- 부품·핀·전압을 코드나 문서에서 임의로 추정해 고정 요구조건으로 만들지 않는다.

## 3. PC 성능과 Pi 실측 구분
- PC에서 측정한 처리시간을 클럭 비율로 환산해 Pi 성능으로 확정하지 않는다.
- Pi 처리성능은 실제 보드에서 별도 측정한 값만 사용한다.

## 4. 형상관리
- 기존 저장소라면 코드 수정 전에 현재 commit과 `git status`를 확인한다.
- 모든 실행 결과 로그에 코드 commit(또는 버전), 설정·의존성 버전, seed를 기록한다.

## 5. 유효성 분리 원칙
- 중심 추적 유효성(`track_valid`)과 크기 측정 유효성(`size_valid`)을 분리한다.
- 가림·팽창·화면 잘림 상태에서는 크기 기반 거리·속도를 무효 처리한다.
- 상태는 최소 `SEARCH`, `TRACK`, `OCCLUDED`, `CLIPPED`, `INFLATING`, `LOST`로 구분한다.

## 6. 절대량 확정 금지
- 카메라 보정과 유효 투영 치수가 없으면 절대 거리와 m/s를 확정 출력하지 않는다.
- 크기 변화율과 `접근/유지/이격` 판별을 우선 사용한다.

## 7. 회귀시험
- 오류가 수정되면 그 오류를 재현한 입력(영상·패킷)을 회귀 세트에 추가한다.
- 수정 기록에는 원인 가설, 변경 내용, 동일 입력의 수정 전후 결과를 남긴다.

## 8. 개발 Gate (K1–K5)
- K1–K5는 이 개발 제안 내부 단계이며 프로젝트 Gate(G0–G9)를 대체하지 않는다.
- "코드가 실행된다"는 사실과 "프로젝트 Gate 통과"를 구분한다.
